# ticket join bundle

Generated by the gateway (Gateway operations › Modules › ticket › Add).

    docker compose up -d

It runs ticket with its own TimescaleDB and RustFS (attachments), both over
TLS with this bundle's local CA, and joins the core's event bus. ticket
applies its migrations and creates its bucket on start.

`private/` holds credentials (the single-use enrolment token, the bundle's
TLS keys); `.env` holds generated passwords, the KEK and the SMTP password.
Keep both on this host only, and back up `.env` with the `ticket-db` and
`ticket-rustfs` volumes: the KEK seals stored data.

Inbound mail: your MTA posts each message to
`https://<this host>:<port>/inbound/mail` (port from `TICKET_INBOUND_LISTEN`)
with `Authorization: Bearer <relay token>` and `Content-Type: message/rfc822`;
the certificate is the one in `TICKET_INBOUND_TLS_DIR` (read at start:
restart `ticket` after renewing it). The relay token is generated once on this
host:

    docker compose exec ticket cat /secrets/relay.token

Rotate it with `docker compose run --rm --entrypoint sh ticket-init -c 'rm
/secrets/relay.token'` and `docker compose up -d`, then update the MTA. After
changing the SMTP password in `.env`, run `docker compose up -d` again.

Core prerequisites: on the core, auth's policy must allow
`spiffe://<trust domain>/svc/ticket` to call
`auth.v1.Profiles/Lookup` and `auth.v1.Profiles/ListMembers` (assignable
agents).

ticket joins the core's event bus (Valkey, TLS) as user `ticket`: the core's
Valkey must accept that user from this host (the address, its password and
the CA file you gave in the wizard). The gateway reads the module's
`platform:events:<tenant>` stream there to send live updates to browsers.

The relay token and SMTP password are host-local files, so warden is not
used; `env` stays `dev` for that reason (production mode refuses `file:` secret references), while
every production guard (TLS everywhere, verified enrolment) is met.
